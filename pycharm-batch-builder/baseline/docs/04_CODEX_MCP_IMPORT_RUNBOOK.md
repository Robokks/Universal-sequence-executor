# Codex + LabVIEW MCP Import and Verification Runbook

**Goal:** Convert the 28 generated AIXML function specifications into native VIs on a LabVIEW PC, verify each, then integrate them as utility subVIs into the full universal executor.

**Critical:** Do NOT connect the prototype to real VTU outputs. Begin with a separate scratch project and a simulated plant.

## 1. Prerequisites

- LabVIEW 2025/2026 installed and licensed on Windows, with the compatible NI AI/grpc integration required by the selected MCP backend.
- Zuehlke/labview-mcp installed; Codex configured to launch the matching `LabVIEWMCP.exe`.
- A Git-controlled work directory with this ZIP extracted and a separate `NativeGenerated` directory.
- Working `lvai_status` or repository self-test on the actual LabVIEW installation.
- A separate simulation-only test project; the physical VFD, servo and PRV interfaces must not be bound during early verification.

The older working MCP version on this machine was reportedly v2.4.1. Do not silently switch versions; first verify the installed executable and its tool schemas. Refer to [repository quickstart](https://github.com/Zuehlke/labview-mcp).

## 2. Phase 0 — Choose the correct AIXML variant

1. Start LabVIEW and connect Codex to LabVIEW MCP.
2. Call `lvai_status`, `lvai_aixml_reference` and `lvai_connector_pane` **without** `viPath`.
3. If the pane is **4815**, choose `aixml/4815` only; if **4833**, choose `aixml/4833` only.
4. If a different pane is configured, stop and regenerate AIXML with a verified connector-pane index map.
5. Inspect `manifest.json` for the source, file hashes, VI list and requirement references.

## 3. Phase 1 — Import a simple VI before the full batch

Suggested first VI: `UE_Relative_Target.aixml`.

1. Read its XML and its catalog entry in `02_COMPLETE_VI_CATALOG.md`.
2. Call `lvai_check_aixml` on the source.
3. Call `lvai_validate_aixml` on the source and inspect the resulting error code and diagnostics.
4. Use `lvai_generate_vi` or `lvai_convert_aixml_to_vi` to create **a new VI in a scratch path**, not on top of any existing VI. Use the exact MCP tool argument schema currently advertised by your installation.
5. Inspect the connector pane using `lvai_connector_pane` with the created VI path. Check every data terminal is on its intended side.
6. Query executable state using `lvai_exec_state`; successful generation alone is insufficient.
7. Run the VI through the supported MCP execution/read-values tool with the exact test inputs from the catalog.
8. Export the generated VI back to AIXML and review important terminal and node changes.
9. Record evidence in `Native_Validation_Log.csv`: tool version, LabVIEW version, VI path, step, results and reviewer.
10. Commit the verified VI and AIXML to Git.

## 4. Phase 2 — Convert in dependency-safe batches

Pure VIs in this package have **no inter-VI call dependencies**, so conversion order can be arranged by complexity:

- **Batch A — Arithmetic:** Relative Target, Measured Displacement, Elapsed, Milliseconds to Seconds, Target Error, Event Duration.
- **Batch B — Conditions:** Inclusive Range, Clamp to Limits, Within Tolerance, Timeout, Stabilization, Dwell, Retry, Cycle completion.
- **Batch C — Logic:** Stop Request, Select Setpoint, TriState, Command Permitted, Capture Acceptable, Operating Point Ready, Can Advance Step, Run ID Matches.
- **Batch D — VTU calculations:** Relative Target Check, Sweep Target, Hydraulic Power, Percent Drop, Load Fraction, Feedback Freshness.

**Do not convert the entire batch in one unreviewed mutation.** Stop if any item does not validate, compiles broken, has a wrong connector pane, or fails a native test.

## 5. Phase 3 — Assemble the real application in LabVIEW

The following are **NOT** generated by this ZIP:

- `.lvproj`, `.lvclass`, actor messages, Actor Core overrides and class-private data bindings.
- The Supervisor, Executor, Bridge, Plugin Adapter, Logger, Parameter Registry, Host editor, network transport and HAL interfaces.
- Timed RT controllers and hardware safety functions.

Create these through LabVIEW's native project tools (assisted by the MCP methods such as `lvai_create_class`, `lvai_create_override`, `lvai_create_message_class`, `lvai_af_add_hook`). Use a small Supervisor–Bridge–SimPlant prototype first. The complete integration build order is defined in `07_ACTOR_FRAMEWORK_ASSEMBLY.md`.

## 5A. Optional DynasBrain preflight and postflight

If the user wants Codex to reuse or modify existing project VIs, connect the read-only DynasBrain MCP server alongside Zuehlke LabVIEW MCP, and ingest the existing LabVIEW project first. Before any mutating operation, query `get_vi` and `get_callers` to identify interface and typedef dependencies. After native AIXML generation and tests, ingest the generated VI and compare the dependency graph. See [`09_DYNASBRAIN_REPOSITORY_REVIEW_AND_INTEGRATION.md`](09_DYNASBRAIN_REPOSITORY_REVIEW_AND_INTEGRATION.md). **Do not treat bridge metadata as compile-test evidence.**

## 6. Stop conditions

- Validation `errorCode` nonzero, non-executable native VI, unexpected coercion or broken wire.
- Incorrect connector-pane mapping, wrong default-value type, missing typedef link, corrupted class ownership or unresolved subVI dependency.
- Any command path that can reach physical hardware before the approved rig safety review.
- Any failed edge-case native test. Do not accept an XML-only pass as a native VI pass.
